## Path, Files y texto

### Qué se ve

Antes de hablar de CSV o JSON hay que saber abrir un fichero, leerlo y cerrarlo bien. Este tema separa dos preguntas que al principio parecen la misma: dónde está el fichero y cómo lo abro, y cómo interpreto lo que hay dentro. La primera la resuelve Java con `Path` y `Files`. La segunda la resolverán las librerías de los temas siguientes.

### Conceptos

Un <mark>Path</mark> es la descripción de una ruta. Crearlo no abre ni comprueba nada: `Path.of("data", "productos.csv")` es válido aunque la carpeta `data` no exista. Por eso se construye con varias partes y no pegando cadenas con `"/"` o `"\\"`; Java pone el separador que toque en cada sistema operativo.

Las rutas pueden ser absolutas (`C:\...` o `/home/...`) o relativas (`data/productos.csv`). Una ruta relativa se resuelve desde el <mark>directorio de trabajo</mark>, que es la carpeta desde la que se lanzó el programa, no la carpeta del `.java`. Ese detalle explica el error más repetido del tema: el programa funciona desde el IDE y falla desde la terminal, o al revés, porque cada uno arranca en una carpeta distinta. Imprimir `path.toAbsolutePath()` dice exactamente qué fichero está intentando abrir Java.

`Path` también sabe trabajar con rutas sin tocar el disco:

| Método | Qué hace |
|---|---|
| `resolve("x.csv")` | Añade un trozo a la ruta |
| `getParent()` / `getFileName()` | Carpeta que la contiene y nombre del fichero |
| `normalize()` | Quita los `.` y `..` sobrantes |
| `relativize(otra)` | Calcula cómo llegar de una ruta a otra |
| `toAbsolutePath()` | La ruta completa desde la raíz |

La clase `Files` es la que actúa sobre el sistema de ficheros: comprueba (`exists`, `isRegularFile`), crea (`createFile`, `createDirectory`, `createDirectories`), copia, mueve, borra y lee o escribe. La diferencia entre `createDirectory` y `createDirectories` importa: la primera falla si falta la carpeta padre, la segunda crea todo el camino y no protesta si ya existe.

Para texto hay tres formas de leer, según el tamaño del fichero:

- `Files.readString(path)` carga todo en un `String`. Cómodo para ficheros pequeños.
- `Files.readAllLines(path)` devuelve una `List<String>`, también con todo en memoria.
- `Files.lines(path)` devuelve un `Stream<String>` que va leyendo según se pide. Sirve para ficheros grandes, pero deja el fichero abierto hasta que se cierra el stream.

En todas conviene pasar `StandardCharsets.UTF_8`. Hasta Java 17 el juego de caracteres por defecto dependía del sistema (en Windows solía ser `windows-1252`), así que un fichero con tildes escrito en un equipo salía con símbolos raros en otro. Java 18 cambió el valor por defecto a UTF-8, pero escribirlo de forma explícita deja claro qué se espera y funciona igual en cualquier versión.

Leer o escribir puede fallar por muchas razones ajenas al programa: el fichero no existe, no hay permisos, el disco está lleno. Java las agrupa en <mark>IOException</mark>, una excepción comprobada: el compilador obliga a capturarla o a declararla con `throws`. Capturarla solo tiene sentido si se puede hacer algo útil, como dar un mensaje con la ruta o devolver un valor por defecto. Un `catch` vacío esconde el error y deja el programa en un estado que nadie entiende.

Lo que se abre hay que cerrarlo, también si algo falla a mitad. Para eso está el <mark>try-with-resources</mark>: los recursos declarados entre los paréntesis del `try` se cierran solos al salir del bloque, en orden inverso al de apertura, haya excepción o no. Funciona con cualquier clase que implemente `AutoCloseable`, que incluye lectores, escritores, streams y los parsers de CSV que vienen después.

El último concepto del bloque es Maven. Java trae `Path`, `Files` y `Properties`, pero no un lector de CSV completo ni Jackson para JSON y XML. Esas librerías se declaran como <mark>dependencias</mark> en el `pom.xml` y Maven las descarga y las pone en el classpath. Un `import` no descarga nada: solo dice qué clase se usa, y si la dependencia no está en el `pom.xml` el `import` no compila.

public String extension(Path path) {
    String archivo = nombre(path);           // getFileName() de la ruta
    int punto = archivo.lastIndexOf('.');
    if (punto == -1) {

Y así queda una lectura con try-with-resources. El `BufferedReader` se cierra al salir del bloque aunque `readLine()` lance una excepción:

```java
Path fichero = Path.of("data", "entrada.txt");
try (BufferedReader reader = Files.newBufferedReader(fichero, StandardCharsets.UTF_8)) {
    System.out.println(reader.readLine());
} catch (IOException e) {
    System.out.println("No se pudo leer " + fichero.toAbsolutePath() + ": " + e.getMessage());
}
```

### Errores típicos

- **Pegar rutas con `"/"`.** Funciona en Linux y falla en Windows, o al revés. `Path.of("data", "productos.csv")` o `carpeta.resolve("productos.csv")` lo evitan.
- **No encontrar un fichero que sí existe.** Casi siempre es el directorio de trabajo. Imprime `toAbsolutePath()` y compara con dónde está de verdad.
- **Tildes rotas al leer.** El fichero se escribió con un juego de caracteres y se leyó con otro. Pasa `StandardCharsets.UTF_8` al leer y al escribir.
- **Usar `Files.lines` fuera de un try-with-resources.** El fichero queda abierto. En Windows eso impide después borrarlo o moverlo.
- **`createDirectory` con carpetas anidadas.** Lanza `NoSuchFileException` si falta el padre. Usa `createDirectories`.

## CSV y el primer CRUD

### Qué se ve

Con un modelo `Producto` y la librería Apache Commons CSV se monta el primer CRUD completo: listar, buscar, crear, modificar y borrar productos guardados en `productos.csv`. Todo va en una sola clase, `CsvCrudDemo`, a propósito: el tema 3 parte de ella para ver qué hay que separar.

### Conceptos

El <mark>modelo</mark> es la clase que representa los datos de la aplicación, sin saber nada de ficheros. En la ruta del profesor es un `record`:

```java
public record Producto(Long id, String nombre, Double precio) {}
```

Un `record` genera solo el constructor, los métodos de acceso (`id()`, `nombre()`, `precio()`), `equals`, `hashCode` y `toString`. Sus campos no se pueden cambiar después de crearlo, así que modificar un producto significa crear otro con los valores nuevos y sustituirlo en la lista. El mismo `Producto` se usará con CSV, JSON y XML, y eso permite ver qué cambia de verdad al cambiar de formato.

Un fichero <mark>CSV</mark> guarda una tabla en texto: una línea por registro y los campos separados por comas, normalmente con una primera línea de cabecera.

```text
id,nombre,precio
1,Teclado,49.99
2,"Monitor, 27 pulgadas",219.90
```

La segunda fila parece tener cuatro campos, pero la coma de `"Monitor, 27 pulgadas"` va entre comillas y forma parte del texto. Esas reglas de comillas y escapes están recogidas en la RFC 4180, y son la razón de no leer un CSV real con `linea.split(",")`: en cuanto un nombre lleva una coma, el `split` parte el campo en dos y los precios acaban en la columna equivocada.

Apache Commons CSV ya conoce esas reglas. Se usa con cuatro piezas:

| Clase | Para qué sirve |
|---|---|
| `CSVFormat` | Describe el dialecto: separador, si hay cabecera, qué columnas escribir |
| `CSVParser` | Recorre el fichero y entrega los registros ya interpretados |
| `CSVRecord` | Una fila; sus campos se leen por nombre de columna con `get("precio")` |
| `CSVPrinter` | Escribe filas poniendo comillas y escapes cuando hacen falta |

Leer por nombre de columna en lugar de por posición tiene una ventaja: si alguien reordena las columnas del fichero, el código sigue funcionando. Para eso el formato de lectura se configura con `setHeader()` (la primera fila son los nombres) y `setSkipHeaderRecord(true)` (no devolverla como dato).

El parser solo convierte texto en campos. Pasar `"49.99"` a `Double`, decidir qué hacer con una fila vacía o rechazar un precio negativo es trabajo de la aplicación, y conviene distinguir los <mark>errores de formato</mark> (el fichero está mal escrito) de los <mark>errores de negocio</mark> (el fichero es correcto pero el dato no vale).

Con lectura y escritura resueltas, el CRUD sigue siempre el mismo esquema: cargar toda la colección, cambiar lo que toque en memoria y reescribir el fichero si hubo cambios. Para un catálogo de clase es suficiente; con millones de filas no lo sería, porque cada operación lee y escribe el fichero entero.

public List<Producto> findAll() throws IOException {
    if (Files.notExists(path)) return new ArrayList<>();
    List<Producto> result = new ArrayList<>();
    try (Reader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8);
         CSVParser parser = inputFormat.parse(reader)) {
        for (CSVRecord row : parser) {
            result.add(new Producto(
                    Long.parseLong(row.get("id")),
                    row.get("nombre"),
                    Double.parseDouble(row.get("precio"))));
        }
    }
    return result;
}

public boolean update(Producto producto) throws IOException {
    List<Producto> items = findAll();                 // lee el fichero entero
    for (int i = 0; i < items.size(); i++) {
        if (items.get(i).id() == producto.id()) {
            items.set(i, producto);                   // el record no se modifica: se sustituye
            saveAll(items);
            return true;
        }
    }
    return false;
}

### Errores típicos

- **Leer con `split(",")`.** Rompe cualquier campo que lleve comas o comillas. Usa `CSVParser`.
- **Construir líneas con `+ ","`.** Es el mismo problema al escribir; `CSVPrinter` pone las comillas por ti.
- **Recibir la cabecera como si fuera un producto.** `Long.parseLong("id")` lanza `NumberFormatException`. Falta `setSkipHeaderRecord(true)`.
- **Precios con coma decimal.** `Double.parseDouble("49,99")` falla. En el fichero los decimales van con punto.

## Del CRUD al repositorio

### Qué se ve

`CsvCrudDemo` funciona, pero mezcla cuatro trabajos en una clase: dónde está el fichero, cómo se lee CSV, cómo se convierte una fila en `Producto` y la lógica del CRUD. Este tema la reparte en piezas sin cambiar lo que hace. Al final, la parte de CSV queda reducida a dos métodos.

### Conceptos

Un <mark>repositorio</mark> es la clase que esconde dónde y cómo se guardan los datos. El resto del programa le pide "dame todos" o "guarda este" y no sabe si detrás hay un CSV, un JSON o una base de datos. Es la idea que se repite en toda la asignatura: en la UT2 el repositorio usará JDBC y en la UT3 JPA, y el código que lo llama casi no cambiará.

La refactorización sale de mirar qué se repite en las cinco operaciones de `CsvCrudDemo`. Todas siguen el mismo patrón: leer la colección, buscar, añadir, sustituir o quitar, y escribir si hubo cambios. Solo dos momentos dependen del formato: convertir el fichero en una lista y convertir la lista en fichero. De ahí salen las piezas:

1. Un <mark>contrato</mark>, la interfaz `IRepository<T, ID>`, con las cinco operaciones y sin mencionar ficheros. No declara `throws IOException`, porque quien usa el repositorio no tiene por qué saber que hay ficheros; si algo falla al leer, la implementación lo convierte en una excepción no comprobada.
2. Una interfaz de dominio, `IProductoRepository extends IRepository<Producto, Long>`, que fija los tipos para productos y es la que usa el resto del programa.
3. Una clase abstracta, `AbstractFileRepository<T, ID>`, con todo el CRUD hecho sobre una lista en memoria. Deja dos métodos sin implementar, `readAll()` y `writeAll()`.
4. Las clases concretas, como `CsvProductoRepository`, que solo rellenan esos dos métodos.

A este reparto se le llama <mark>patrón plantilla</mark> (template method): la clase madre fija los pasos del algoritmo y las hijas aportan los que cambian. El beneficio se ve en el tema siguiente, cuando JSON y XML se añaden escribiendo solo `readAll` y `writeAll`.

Hay otro cambio de comportamiento. `CsvCrudDemo` relee el fichero en cada búsqueda; el repositorio lo lee una vez, guarda la lista en memoria y solo escribe cuando algo cambia. Es más rápido, con una contrapartida que conviene tener presente: si otro programa modifica el fichero mientras el repositorio está abierto, el repositorio no se entera.

```java
public abstract class AbstractFileRepository<T extends Identifiable<ID>, ID>
        implements IRepository<T, ID> {

    protected abstract List<T> readAll();
    protected abstract void writeAll(List<T> elements);

    @Override
    public boolean create(T element) {
        if (element == null || element.id() == null || findById(element.id()).isPresent()) {
            return false;
        }
        lista().add(element);
        writeAll(lista());
        return true;
    }

    @Override
    public Optional<T> findById(ID id) {
        if (id == null) return Optional.empty();
        // equals y no == : con Long, == compara objetos
        return lista().stream().filter(p -> p.id().equals(id)).findFirst();
    }
}
```

### Errores típicos

- **Comparar ids `Long` con `==`.** `==` compara si son el mismo objeto. Java reutiliza los `Long` entre -128 y 127, así que con ids pequeños parece funcionar y a partir de 128 deja de encontrar productos. Con objetos, siempre `equals` (o `Objects.equals` si puede haber `null`).

- **Dejar `throws IOException` en la interfaz.** Obliga a todo el programa a tratar errores de ficheros aunque mañana el repositorio use una base de datos.
- **Devolver la lista interna en `findAll()`.** Quien la recibe podría cambiarla sin pasar por el repositorio. Devuelve una copia.

## JSON y XML con Jackson

### Qué se ve

Los mismos productos, ahora en JSON y en XML. La librería Jackson se encarga de convertir objetos Java en texto y al revés en los dos formatos. Gracias al tema anterior, cada formato nuevo es una clase con `readAll` y `writeAll`.

### Conceptos

<mark>JSON</mark> representa datos con objetos (`{ }`), arrays (`[ ]`), textos, números, booleanos y `null`. A diferencia del CSV, conserva la estructura y distingue un número de un texto. El catálogo es un array donde cada elemento es un producto:

```json
[
  { "id": 1, "nombre": "Teclado", "precio": 49.99 },
  { "id": 2, "nombre": "Monitor", "precio": 219.9 }
]
```

| JSON | Java |
|---|---|
| objeto | un objeto o un `record` |
| array | `List<T>` |
| texto | `String` |
| número | `int`, `long`, `double`… |
| `true` / `false` | `boolean` |
| `null` | `null` |

Pasar de objeto a texto se llama <mark>serializar</mark>, y de texto a objeto, <mark>deserializar</mark>. En Jackson las dos cosas las hace un `ObjectMapper` (dependencia `jackson-databind`): `writeValue` serializa y `readValue` deserializa. Jackson empareja los nombres de las propiedades del JSON con los del modelo, y desde la versión 2.12 entiende los `record` sin anotaciones. Crear un `ObjectMapper` es costoso y, una vez configurado, se puede compartir, así que se guarda como atributo y no se crea en cada llamada.

Para leer una lista hay un detalle. Escribir `List.class` no basta, porque en ejecución Java borra los tipos genéricos (se llama <mark>borrado de tipos</mark>) y Jackson no sabría que los elementos son `Producto`. La solución es `new TypeReference<List<Producto>>() {}`, una clase anónima que conserva el tipo completo.

<mark>XML</mark> organiza los datos como un documento de etiquetas anidadas, y exige un único elemento raíz que lo envuelva todo:

```xml
<productos>
  <producto>
    <id>1</id>
    <nombre>Teclado</nombre>
    <precio>49.99</precio>
  </producto>
</productos>
```

Jackson también lo lee y escribe con `XmlMapper` (dependencia `jackson-dataformat-xml`), que tiene la misma forma de uso que `ObjectMapper`. La diferencia es esa raíz: una `List<Producto>` no tiene dónde poner `<productos>`. Por eso se crea una <mark>clase envoltorio</mark> que representa el documento entero y contiene la lista. Dos anotaciones ajustan el resultado:

- `@JacksonXmlRootElement(localName = "productos")` da nombre a la raíz.
- `@JacksonXmlElementWrapper(useWrapping = false)` evita que Jackson meta la lista dentro de otra etiqueta más, de forma que cada `<producto>` cuelgue directamente de `<productos>`.

Con eso, CSV, JSON y XML quedan como tres maneras de escribir lo mismo:

| | CSV | JSON | XML |
|---|---|---|---|
| Forma | tabla | objetos y arrays | documento jerárquico |
| Leer | `CSVParser` | `ObjectMapper` | `XmlMapper` + envoltorio |
| Escribir | `CSVPrinter` | `ObjectMapper` | `XmlMapper` + envoltorio |
| El CRUD | `AbstractFileRepository` | igual | igual |

## Un repositorio para cualquier entidad

### Qué se ve

Hasta aquí todo giraba en torno a `Producto`. Este tema comprueba que `AbstractFileRepository` sirve también para otra entidad, `Vehiculo`, cuyo identificador es una matrícula de tipo `String`. Para eso la clase abstracta necesita saber sacar el id de cualquier objeto, y en clase vimos tres formas de hacerlo.

### Conceptos

Los <mark>genéricos</mark> permiten escribir una clase una vez y usarla con distintos tipos. En `AbstractFileRepository<T, ID>`, `T` es la entidad y `ID` el tipo de su identificador: `<Producto, Long>` para productos y `<Vehiculo, String>` para vehículos. El compilador comprueba los tipos en cada uso, así que no se puede guardar un `Vehiculo` en el repositorio de productos.

El problema es que dentro de la clase abstracta `T` puede ser cualquier cosa, y para buscar, actualizar o borrar hace falta el id. Las tres soluciones que aparecen en los ejercicios:

| Solución | Dónde | Cómo se obtiene el id |
|---|---|---|
| Interfaz `Identifiable<ID>` | `catalogo` | La entidad implementa `id()`; el genérico se restringe con `T extends Identifiable<ID>` |
| `Function<T, ID>` | ruta del profesor | Cada repositorio pasa al constructor cómo sacarlo, por ejemplo `Producto::id` |
| Método abstracto `getId(T)` | examen RA1 | Cada repositorio hijo lo implementa |

Las tres funcionan. `Identifiable` obliga a tocar el modelo, pero a cambio el compilador garantiza que toda entidad tiene id. `Function` deja el modelo intacto y encaja con entidades cuyo id no se llama `id`, como `Vehiculo::matricula`. El método abstracto es la opción más sencilla de leer, aunque repite una línea en cada hijo.

El caso de `Vehiculo` también sirve para hablar de validación. En la ruta del profesor el `record` revisa sus datos en el constructor compacto y normaliza la matrícula a mayúsculas, de forma que `"1234abc"` y `"1234ABC"` son el mismo vehículo:

```java
public record Vehiculo(String matricula, String marca, String modelo, int anio) {
    public Vehiculo {
        if (matricula == null || matricula.isBlank()) {
            throw new IllegalArgumentException("La matrícula es obligatoria");
        }
        matricula = matricula.trim().toUpperCase();
    }
}
```

## Elegir el formato con .properties

### Qué se ve

El último paso saca de Java la decisión de qué formato y qué fichero usar. Un fichero `.properties` dice "csv" o "json", y una clase lee esa configuración y crea el repositorio que toca. Cambiar de formato pasa a ser editar una línea, sin recompilar.

### Conceptos

Un fichero <mark>.properties</mark> guarda configuración como pares `clave=valor`, una por línea, con `#` para los comentarios. Java lo lee con la clase `Properties`:

```properties
# data/app.properties
app.name=FileLab
storage.format=json
storage.path=data/productos.json
```

`getProperty("storage.format")` devuelve el valor como texto, o `null` si la clave no existe. Existe una segunda versión con valor por defecto, `getProperty("storage.format", "csv")`, que evita los `null` cuando falta una línea.

Al cargar el fichero hay un detalle con las tildes. `Properties.load(InputStream)` lee el fichero como ISO-8859-1, el juego de caracteres histórico de este formato, y una "ó" escrita en UTF-8 sale rota. `Properties.load(Reader)` usa el juego de caracteres del lector, así que con `Files.newBufferedReader(path, StandardCharsets.UTF_8)` las tildes llegan bien.

Con la configuración leída, falta una pieza que convierta el texto `"json"` en un objeto `JsonRepository`. Esa pieza es una <mark>factoría</mark>: un método cuyo único trabajo es crear el objeto adecuado según un dato. El resto del programa recibe un `IProductoRepository` y no sabe cuál le ha tocado. En los ejercicios aparecen dos versiones:

- En `catalogo`, una cadena de `if` sobre el texto del `.properties`.
- En `file-lab`, un `enum FileFormat` con los formatos válidos y un `switch` sobre él. Si mañana se añade un formato al `enum` y no al `switch`, el compilador avisa.

La ruta del profesor termina con el proyecto DataBridge, que junta todo lo de la unidad: leer productos de un formato y escribirlos en otro (de CSV a JSON, de JSON a XML…) eligiendo origen y destino por configuración.

### Errores típicos

- **Leer el `.properties` con `load(InputStream)`.** Las tildes del fichero salen como `Ã³`. Usa un `Reader` en UTF-8.
- **No dar valor por defecto.** `getProperty` devuelve `null` si falta la clave, y el `NullPointerException` aparece lejos de la causa.
- **Formato mal escrito en el fichero.** `"JSON "` con un espacio no coincide con `"json"`. Recorta y compara sin distinguir mayúsculas, como hace `FileFormat.from`, y lanza un error que diga qué valor llegó.
- **La ruta del `.properties` también es relativa.** Se resuelve desde el directorio de trabajo, igual que en el tema 1.

### Repaso rápido

<details>
<summary>¿Qué devuelve `getProperty("clave")` si la clave no está en el fichero?</summary>

`null`. Con `getProperty("clave", "valor")` devuelve el valor por defecto.

</details>
<details>
<summary>¿Por qué la factoría devuelve `IProductoRepository` y no la clase concreta?</summary>

Para que el código que la usa no dependa del formato. Si devolviera `JsonRepository`, cambiar a CSV obligaría a tocar también ese código.

</details>
<details>
<summary>¿Qué ventaja tiene el `switch` sobre un `enum` frente a la cadena de `if`?</summary>

Que el compilador comprueba que están todos los casos, y que los valores posibles están escritos en un solo sitio.

</details>
