## Cómo es el examen

### Qué se ve

El examen tiene dos partes. La primera es **tipo test, de 70 preguntas**: preguntas de elegir una opción, de relacionar conceptos con su definición y de ordenar los pasos de un proceso. La segunda es de **desarrollo**: explicar con palabras propias cómo se despliega una aplicación con Kamal y, en general, todo lo visto hasta ahora.

Aunque la web del módulo dice que el primer examen trimestral cubre la UT1 y la UT2, las preguntas de ejemplo de clase tocan las seis unidades (FTP, DNS y LDAP incluidos) y el caso práctico de Kamal con JWT y Alembic. Por eso esta página las repasa todas.

Abajo hay **70 preguntas**, como en el examen. Las **38 marcadas con ★** son las que el profesor confirmó que saldrán; aquí están con sus mismas opciones y una explicación propia de cada respuesta. Las otras 32 salen de las preguntas de ejemplo que se dictaron en clase el 24/11 y del temario, con el mismo nivel.

### Errores típicos

- **Confundir codificar con cifrar.** Base64 (Basic Auth) y base64url (JWT) se deshacen sin ninguna clave. Solo TLS (HTTPS) cifra lo que viaja.
- **Confundir autenticación con autorización.** La primera comprueba quién eres; la segunda decide qué puedes hacer. Siempre va primero la autenticación.
- **Creer que `EXPOSE` publica un puerto.** Solo lo documenta. Publicar es `-p` en Docker o el proxy en Kamal.
- **Creer que `kamal rollback` deshace la migración.** Solo vuelve al contenedor anterior. La base de datos se deshace aparte, con `alembic downgrade` o restaurando la copia.

### Preguntas tipo test

**1. Una aplicación con nginx, Gunicorn y PostgreSQL se organiza por capas. ¿Qué asignación es la correcta?**

- a) Cliente → lógica → presentación → datos
- b) Cliente → nginx → PostgreSQL → lógica
- c) Cliente → presentación (nginx) → lógica (Gunicorn) → datos (PostgreSQL)
- d) Cliente → datos → lógica → presentación

<details>
<summary>Respuesta</summary>

**c)**. La petición entra por nginx, que es la puerta (presentación). Si es dinámica, la pasa a Gunicorn, que ejecuta el código (lógica). El código consulta PostgreSQL (datos). La respuesta vuelve por el mismo camino.

- a) pone la lógica antes que nginx, pero el cliente nunca habla directamente con Gunicorn.
- b) pone la base de datos antes que la lógica: PostgreSQL no sabe recibir peticiones HTTP, solo consultas SQL que le manda la aplicación.
- d) está al revés.

</details>

**2. ¿Qué aporta HTTPS a HTTP?**

- a) Comprime las páginas para que pesen menos
- b) Cifra la comunicación y permite comprobar la identidad del servidor con un certificado
- c) Sustituye TCP por UDP
- d) Hace que la página cargue sin servidor

<details>
<summary>Respuesta</summary>

**b)**. HTTPS es HTTP dentro de una conexión TLS. TLS cifra lo que viaja (nadie en medio puede leerlo) y el certificado demuestra que el servidor es quien dice ser.

- a) La compresión es otra cosa (gzip, brotli) y existe también sin TLS.
- c) HTTPS sigue yendo sobre TCP. El que usa UDP es HTTP/3, a través de QUIC.
- d) No tiene sentido: siempre hace falta un servidor.

</details>

**3. ¿Qué diferencia hay entre un servidor web como nginx y un servidor de aplicaciones como Gunicorn?**

- a) Ninguna, son nombres distintos para lo mismo
- b) nginx sirve ficheros estáticos y hace de proxy; Gunicorn ejecuta el código de la aplicación Python
- c) nginx ejecuta Python y Gunicorn sirve imágenes
- d) Gunicorn es la base de datos de nginx

<details>
<summary>Respuesta</summary>

**b)**. nginx entrega HTML, CSS, imágenes y reenvía lo dinámico. No sabe ejecutar Python. Gunicorn carga la aplicación (Flask, Django) y genera la respuesta ejecutando su código. Trabajan juntos: ninguno sustituye al otro.

- a) y c) son falsas por lo anterior.
- d) Gunicorn no guarda datos; eso es PostgreSQL.

</details>

**4. ¿Qué es WSGI?**

- a) Un contrato entre el servidor y la aplicación Python que define cómo se le entrega cada petición y cómo devuelve la respuesta
- b) El sistema de PostgreSQL que aplica cambios al esquema
- c) El módulo de nginx que sirve estáticos
- d) El formato de plantillas HTML que usa Django

<details>
<summary>Respuesta</summary>

**a)**. WSGI (Web Server Gateway Interface, PEP 3333) es la norma de Python que dice qué objeto expone la aplicación y cómo la llama el servidor. Gracias a ella, cualquier aplicación compatible funciona con cualquier servidor compatible. En Flask el objeto es `app` (se arranca con `gunicorn app:app`) y en Django `config.wsgi:application`.

- b) Eso serían las migraciones (Alembic en Python).
- c) nginx sirve estáticos con su núcleo, sin WSGI.
- d) Las plantillas de Django son su propio lenguaje de plantillas, no WSGI.

</details>

**5. Gunicorn arranca con `--workers 2`. ¿Qué significa?**

- a) Se crean dos servidores nginx que se reparten el tráfico con DNS
- b) Un proceso maestro lanza dos procesos que ejecutan la aplicación y atienden peticiones a la vez en el mismo puerto
- c) Se ejecutan dos copias de la aplicación en puertos distintos con configuraciones distintas
- d) Gunicorn reintenta dos veces cada petición fallida

<details>
<summary>Respuesta</summary>

**b)**. El maestro lee la configuración, abre el punto de escucha y crea los workers. Los dos comparten el mismo puerto (por ejemplo, el 8000), así que pueden servir dos peticiones a la vez. Si uno muere, el maestro lo repone.

- a) Los workers no tienen nada que ver con nginx ni con DNS.
- c) No hay dos puertos ni dos configuraciones: es la misma aplicación repetida.
- d) Los reintentos no son función de `--workers`.

</details>

**6. nginx recibe una petición dinámica y devuelve 502 Bad Gateway. ¿Cuál es la causa más habitual?**

- a) Gunicorn no está arrancado o `proxy_pass` apunta a una dirección o puerto equivocados
- b) El certificado ha caducado
- c) El cliente no ha enviado la cabecera Host
- d) El fichero HTML no existe

<details>
<summary>Respuesta</summary>

**a)**. 502 quiere decir que nginx, actuando de pasarela, no ha recibido una respuesta válida del servidor de detrás. Lo primero que hay que mirar es si Gunicorn está en marcha (`ps aux | grep gunicorn`) y si responde en la dirección de `proxy_pass` (`curl -I http://127.0.0.1:8000/`).

- b) Un certificado caducado da un aviso de seguridad en el navegador, no un 502.
- c) Sin cabecera Host, nginx usa el sitio por defecto; no da 502.
- d) Un fichero inexistente es 404. Y si Gunicorn tarda demasiado en contestar, el código es 504 (Gateway Timeout), no 502.

</details>

**7. ¿Qué diferencia hay entre una web estática y una aplicación web?**

- a) La estática usa CSS y la aplicación no
- b) La estática entrega ficheros ya hechos, iguales para todos; la aplicación ejecuta código que genera la respuesta en cada petición (por ejemplo, consultando una base de datos)
- c) La estática solo se ve en el ordenador y la aplicación también en el móvil
- d) No hay diferencia si se sirve con nginx

<details>
<summary>Respuesta</summary>

**b)**. Una web hecha con Zensical o Jekyll se compila una vez y nginx entrega el HTML tal cual. Una tienda que muestra los pedidos de cada usuario necesita ejecutar código en cada petición.

- a) y c) describen cosas que valen para las dos.
- d) nginx puede servir las dos, pero la aplicación necesita además un servidor de aplicaciones.

</details>

**8. ¿En qué capa trabaja el protocolo HTTP?**

- a) En la capa de aplicación, sobre TCP
- b) En la capa de red, como IP
- c) En la capa de enlace, con las direcciones MAC
- d) En la capa de transporte, en lugar de TCP

<details>
<summary>Respuesta</summary>

**a)**. HTTP es un protocolo de aplicación (capa 7 de OSI). Usa TCP como transporte (puerto 80, o 443 con TLS). HTTP/3 cambia TCP por QUIC sobre UDP, pero sigue siendo de aplicación.

- b), c) y d) confunden HTTP con los protocolos de las capas de debajo.

</details>

**★ 11. Un sitio con HTTPS tiene un formulario programado con fallos de seguridad. ¿Qué pasa con esos fallos?**

- a) Desaparecen cuando el certificado lo emite una autoridad conocida
- b) Siguen existiendo, porque HTTPS solo protege el canal
- c) HTTPS los corrige al cifrar los datos que viajan
- d) Solo afectan a los usuarios que entran por HTTP

<details>
<summary>Respuesta</summary>

**b)**. TLS cifra lo que viaja entre cliente y servidor. Si el código guarda contraseñas en claro o acepta datos sin validar, eso no cambia por tener candado.

- **Decir que 502 es «el servidor está caído».** Es más preciso: nginx sí funciona, lo que falla es el de detrás. Si nginx estuviera caído, el navegador no podría ni conectar.

### Preguntas tipo test

**18. Dos dominios apuntan a la misma IP, puerto 80. ¿Cómo sabe nginx qué sitio servir?**

- a) Por la IP de origen del cliente
- b) Compara la cabecera Host de la petición con el `server_name` de cada server block; si ninguno coincide, usa el `default_server`
- c) Sirve siempre el primer fichero de `sites-enabled`, sin mirar nada más
- d) Pregunta al DNS cuál toca

<details>
<summary>Respuesta</summary>

**b)**. Es el alojamiento virtual por nombre. El navegador manda `Host: www.ejemplo.local` en cada petición (la cabecera Host existe desde HTTP/1.1 justo para esto) y nginx busca el `server_name` que coincide: primero el nombre exacto, luego comodines y expresiones regulares, y al final el `default_server`.

- a) La IP del cliente no decide el sitio.
- c) El primero solo se usa si nadie lleva `default_server` y ningún nombre coincide.
- d) El DNS ya hizo su trabajo antes: llevar al cliente hasta la IP. nginx no le pregunta nada.

</details>

**19. ¿Para qué sirve `location` en nginx?**

- a) Para indicar la ubicación física del servidor
- b) Para aplicar una configuración distinta según la ruta de la URL pedida (por ejemplo, `/api/` va al backend y `/img/` se sirve del disco)
- c) Para elegir el país del certificado
- d) Para definir el puerto de escucha

<details>
<summary>Respuesta</summary>

**b)**. Dentro de un server block, cada `location` atrapa unas URL. Hay coincidencia exacta (`location = /`), por prefijo (`location /img/`), prefijo prioritario (`^~`) y expresiones regulares (`~` y `~*`). Gana la exacta; si no, el prefijo más largo, salvo que una regex coincida antes.

- a) y c) no tienen nada que ver con nginx.
- d) El puerto se pone con `listen`.

</details>

**20. Basic Auth envía usuario y contraseña en Base64. ¿Qué implica?**

- a) Que la contraseña va cifrada con la clave del servidor
- b) Que no va cifrada: Base64 se decodifica sin clave, así que cualquiera que capture la petición la lee. Hay que usarlo siempre con HTTPS
- c) Que el servidor guarda la contraseña en texto plano
- d) Que el navegador la cifra con su certificado

<details>
<summary>Respuesta</summary>

**b)**. Base64 es una forma de escribir bytes con letras, no un cifrado. La cabecera `Authorization: Basic ...` se puede decodificar con `echo ... | base64 -d`. Por eso las prácticas de la UT3 combinan Basic Auth con HTTPS.

- a) y d) suponen un cifrado que no existe.
- c) El fichero `htpasswd` guarda las contraseñas con hash, no en claro; además, la pregunta trata de cómo viajan, no de cómo se guardan.

</details>

**21. ¿Qué diferencia hay entre un certificado de Let's Encrypt y uno autofirmado?**

- a) El autofirmado cifra con menos bits
- b) El de Let's Encrypt no necesita clave privada
- c) El de Let's Encrypt lo firma una autoridad en la que confían los navegadores; el autofirmado lo firma uno mismo y el navegador avisa de que no es de confianza
- d) El autofirmado es más seguro porque nadie más lo conoce

<details>
<summary>Respuesta</summary>

**c)**. El cifrado es igual de fuerte en los dos. La diferencia es la confianza: Let's Encrypt es una autoridad de certificación gratuita y automatizada (protocolo ACME) que comprueba que controlas el dominio. Por eso exige un dominio público al que pueda llegar. El autofirmado sirve para pruebas en local (`openssl req -x509 ...`) y con curl se prueba usando `-k`.

- a) La longitud de clave la elige quien genera el certificado, no depende de quién firma.
- b) Los dos necesitan clave privada; sin ella no hay TLS.
- d) Que nadie lo conozca es justo el problema: nadie puede comprobarlo.

</details>

**★ 23. ¿Qué función cumple una autoridad certificadora?**

- a) Guardar las contraseñas de los usuarios de un sitio web
- b) Traducir los nombres de dominio
- c) Cifrar cada petición
- d) Firmar certificados

<details>
<summary>Respuesta</summary>

**d)**. La autoridad certificadora (CA) comprueba que quien pide el certificado controla el dominio y lo firma. El navegador trae una lista de CA en las que confía y, si el certificado del sitio está firmado por una de ellas, lo acepta.

**★ 54. Para establecer la conexión segura, FTPS usa cifrado asimétrico. Si el cliente protege un mensaje dirigido al servidor, ¿qué clave usa cada uno?**

- b) El cliente cifra con la clave pública del servidor y el servidor descifra con su clave privada
- c) Los dos usan la misma clave, que viaja en el primer mensaje
- d) El cliente cifra con la clave privada del servidor y el servidor descifra con su pública

<details>
<summary>Respuesta</summary>

**b)**. En el cifrado asimétrico, lo que se cifra con la clave pública de alguien solo se descifra con su clave privada. La pública del servidor va en su certificado, a la vista de todos; la privada nunca sale del servidor.

- a) Cifrar con la privada propia sirve para **firmar**, no para ocultar: cualquiera con la pública podría leerlo.
- c) Esa es una clave simétrica, y mandarla sin protección permitiría leer todo. (Después del saludo sí se usa una clave simétrica de sesión, pero se acuerda de forma segura.)
- d) El cliente nunca tiene la clave privada del servidor.

</details>

### Errores típicos

- **FTPS y SFTP no son lo mismo.** FTPS es FTP con TLS. SFTP no es FTP: es un subsistema de SSH.
- **Un CNAME no puede convivir con otros registros del mismo nombre.** Por eso el dominio raíz de una zona no puede ser un CNAME (tiene SOA y NS).
- **El DN se lee de la hoja a la raíz.** `uid=ana,ou=usuarios,dc=empresa,dc=local`: primero la persona, al final la base del árbol.

## Pregunta de desarrollo: el despliegue con Kamal

### Qué se ve

La segunda parte pide explicar con palabras propias cómo se despliega una aplicación con Kamal. Abajo hay una respuesta modelo, escrita para poder contarla de memoria, sobre el caso práctico de clase: una API de tareas en FastAPI con SQLite, JWT y Alembic.

### Conceptos

**Qué es Kamal.** Una herramienta que despliega una aplicación empaquetada en una imagen Docker en uno o varios servidores propios, entrando por SSH. No hace falta instalar nada en el servidor a mano: si falta Docker, lo instala. La idea es pasar de «funciona en mi ordenador» a «funciona en el servidor, con HTTPS, y publico una versión nueva con un solo comando y sin cortar el servicio».

**Las piezas.**

| Pieza | Para qué sirve |
|---|---|
| `Dockerfile` | Receta de la imagen: Python, dependencias, código y migraciones, usuario sin privilegios, `EXPOSE 8000` y arranque con uvicorn en `0.0.0.0:8000` |
| Registro de imágenes | Almacén donde se sube la imagen (ghcr.io en el ejemplo) para que el servidor la descargue |
| `config/deploy.yml` | Lo común: nombre del servicio, imagen, registro, usuario SSH, arquitectura y `proxy.app_port` |
| `config/deploy.staging.yml` y `deploy.production.yml` | Lo de cada destino: IP del servidor, dominio (`proxy.host`), `ssl: true`, volumen y variables |
| `.kamal/secrets` | Valores secretos (contraseña del registro, `JWT_SECRET_KEY`). No se sube a Git; en el YAML solo va el nombre |
| kamal-proxy | Contenedor que Kamal pone en el servidor. Escucha en el 80 y el 443, gestiona el certificado y reparte por dominio |
| `justfile` | Recetas cortas: `just deploy staging` pasa antes todas las comprobaciones de calidad |

### Casos y ejemplos

**Respuesta modelo (para contarla con mis palabras).**

1. **Antes de desplegar, se comprueba el código.** En el caso práctico, `just deploy` lanza primero `just preflight`: formato y lint con Ruff, tipos con mypy, tests unitarios, de integración y de extremo a extremo con un mínimo de cobertura del 80 %, Bandit para buscar fallos de seguridad en el código, pip-audit para las dependencias y Gitleaks para secretos olvidados en el historial. Si algo falla, no se despliega. El mismo pipeline corre en GitHub Actions con cada push.
2. **Kamal lee la configuración.** Con `kamal deploy -d staging` junta `deploy.yml` con `deploy.staging.yml`. El destino `staging` es un servidor de pruebas parecido al real; `production` es el que ven los usuarios.
3. **Construye la imagen y la sube al registro.** La imagen lleva todo lo necesario para ejecutar la API. Se construye para la arquitectura del servidor (`builder.arch: amd64`).
4. **Entra por SSH en el servidor.** Con el usuario de `ssh.user` y una clave, sin contraseña. El servidor descarga la imagen del registro.
5. **Arranca la versión nueva al lado de la vieja.** El contenedor nuevo monta el volumen `/var/lib/tasks-api:/data`, donde vive la base de datos SQLite, para que los datos no se pierdan al cambiar de contenedor.
6. **Comprueba que está sana.** kamal-proxy pide `GET /up` al contenedor nuevo hasta que responde 200. Mientras tanto, los usuarios siguen en la versión vieja.
7. **Cambia el tráfico y retira la vieja.** Cuando `/up` responde 200, el proxy manda las peticiones al nuevo y Kamal para el viejo. Así no hay corte. Si `/up` no llega a responder, el tráfico se queda en la vieja.
8. **HTTPS automático.** Con `proxy.host` y `ssl: true`, kamal-proxy pide y renueva un certificado de Let's Encrypt para ese dominio. Para eso el DNS del dominio tiene que apuntar a la IP del servidor y los puertos 80 y 443 tienen que estar abiertos (en Oracle Cloud, abriéndolos en las reglas de red de la máquina).
9. **Varias apps en el mismo servidor.** Como el proxy decide por la cabecera Host, en el mismo 80/443 pueden convivir `app1.ejemplo.es` y `app2.ejemplo.es`, cada una en su contenedor. Las apps no publican puertos al exterior: el proxy llega a ellas por la red interna de Docker.
10. **Si sale mal, se vuelve atrás.** `kamal rollback VERSIÓN` vuelve a arrancar el contenedor de una versión anterior, que sigue en el servidor. Ojo: no toca la base de datos.

**Si la versión trae cambios en la base de datos.** La API empezó sin usuarios y luego se añadió el login con JWT, así que hubo que crear la tabla `users` y una columna de dueño en `tasks` con una base que ya estaba en producción. Para eso se usan migraciones con Alembic: cada cambio del esquema es una revisión numerada (`0001_baseline`, `0002_add_users...`), y la tabla `alembic_version` de la base dice en cuál está. `alembic upgrade head` aplica las pendientes y `alembic downgrade -1` deshace la última. Las tareas antiguas no tenían dueño: se decidió asignarlas a un usuario administrador creado durante la propia migración, con usuario y contraseña tomados de variables de entorno. El protocolo completo:

1. Copia de seguridad de la base de datos.
2. Probar la migración en staging: `upgrade`, comprobar la API y probar también el `downgrade`.
3. Elegir una hora con pocos usuarios y, si hace falta, mostrar una página estática de mantenimiento.
4. Aplicar `alembic upgrade head` contra el volumen de producción. La aplicación del ejemplo comprueba al arrancar que la base está en la última revisión y se niega a arrancar si no.
5. Desplegar la versión nueva con `kamal deploy -d production` y comprobar `/up` y los endpoints.
6. Si falla, dos vueltas atrás: la imagen con `kamal rollback` y la base con `alembic downgrade` o restaurando la copia.

**Seguridad en el flujo.** La autenticación (quién eres) ocurre en `POST /auth/token`: el backend compara la contraseña con su hash Argon2 y devuelve un JWT firmado con `sub` (id del usuario), `iat` y `exp`. La autorización (qué puedes hacer) ocurre en cada endpoint protegido: el backend comprueba el token, saca el usuario y solo le deja ver sus tareas. Todo viaja por HTTPS, porque ni la contraseña del login ni el token van cifrados por sí mismos.

### Errores típicos

- **Decir que el host va en el cuerpo de la petición.** Va en la cabecera `Host`, igual que el JWT va en la cabecera `Authorization`.
- **Decir que Kamal migra y deshace la base de datos solo.** En el caso práctico la migración es un paso explícito y `kamal rollback` solo cambia el contenedor.
- **Escribir 433.** El puerto de HTTPS es el 443.
- **Las IP de Docker.** Son privadas: por defecto la red `bridge` usa 172.17.0.0/16, dentro del rango privado 172.16.0.0/12 (los otros rangos privados son 10.0.0.0/8 y 192.168.0.0/16). Dos contenedores pueden escuchar en el mismo puerto porque cada uno tiene su IP.

### Repaso rápido

<details>
<summary>¿Qué diferencia hay entre kamal setup y kamal deploy?</summary>

`setup` se usa la primera vez: prepara el servidor (instala Docker si hace falta, arranca el proxy) y despliega. `deploy` publica una versión nueva en un servidor ya preparado.

</details>
<details>
<summary>¿Por qué existe el endpoint /up?</summary>

Porque es el que consulta kamal-proxy para decidir si la versión nueva está sana. Hasta que no responde 200, no recibe tráfico.

</details>
<details>
<summary>¿Por qué el contenedor no se ejecuta como root?</summary>

Para que, si alguien consigue ejecutar código a través de la aplicación, no tenga permisos de administrador dentro del contenedor. El del ejemplo usa un usuario sin privilegios que solo puede escribir en `/data`.

</details>
<details>
<summary>¿Dónde van los secretos?</summary>

En `.kamal/secrets` (o `.kamal/secrets.staging` y `.kamal/secrets.production` si hay destinos), que no se suben a Git. En `deploy.yml` solo se nombran bajo `env.secret`.

</details>

### Casos y ejemplos

**Redacción modelo (para contarla con mis palabras).**

**1. Todo empieza guardando el trabajo: Git.** Antes de desplegar nada, el proyecto tiene que estar en un sistema de control de versiones. Con Git cada cambio queda en un commit con autor, fecha y motivo, se puede volver atrás y se trabaja en ramas sin romper `main`. Cada práctica del curso es un repositorio propio con un README que cuenta la instalación, la configuración, la comprobación con salidas reales y los problemas encontrados, para que otra persona pueda repetirla. El código ya está guardado y documentado, pero de momento solo lo veo yo: **hay que servirlo para que otros lo vean**.

**2. Lo más sencillo que se puede servir: una web estática.** La documentación se escribe en Markdown y Zensical la compila a HTML, CSS y JavaScript. El resultado son ficheros fijos, iguales para todos. Para entregarlos hace falta alguien que escuche peticiones y conteste: **un servidor web**.

**3. El servidor web: nginx, y dentro de un contenedor.** Aquí entra el modelo cliente-servidor: el navegador pide por HTTP (puerto 80) y el servidor responde con un código de estado y el fichero. nginx es el servidor web del curso: un proceso maestro y varios workers, configuración en `/etc/nginx` y un fichero por sitio en `sites-available`. Para no ensuciar mi equipo y poder repetirlo igual en cualquier sitio, nginx corre en un contenedor Docker (`dpl-lab`): una imagen con todo lo necesario, puertos publicados con `-p` y la carpeta del proyecto montada como volumen. Funciona un sitio, pero en la práctica quería servir la documentación **y** un blog desde el mismo servidor.

**4. Varios sitios, protegidos y cifrados.** Con server blocks por nombre, un solo nginx en un solo puerto sirve varios sitios: el navegador manda la cabecera `Host` y nginx la compara con `server_name` (si no coincide ninguno, responde el `default_server`). Con `location` se decide qué hacer con cada ruta. Algunas zonas no deben ser públicas: se protegen con Basic Auth, que manda la contraseña solo codificada en Base64, así que hace falta cifrar el canal con **HTTPS**: un certificado autofirmado para pruebas y uno de Let's Encrypt en producción. Hasta aquí todo es contenido fijo. Una aplicación de verdad (una API de tareas, una tienda) tiene que **ejecutar código y guardar datos**.

**5. La aplicación: capas, servidor de aplicaciones y base de datos.** nginx no ejecuta Python. Detrás se pone un servidor de aplicaciones, Gunicorn, que habla con la aplicación por WSGI y reparte las peticiones entre sus workers. nginx hace de **proxy inverso**: sirve los estáticos y pasa lo dinámico con `proxy_pass`. Si Gunicorn no responde, el cliente ve un 502. La aplicación guarda sus datos en PostgreSQL, en su propio contenedor y con un **volumen** para que no se pierdan. Compose levanta todo junto. Quedan las cuatro capas: cliente, presentación (nginx), lógica (Gunicorn) y datos (PostgreSQL). Pero todo esto sigue en mi ordenador: **hay que llevarlo a una máquina accesible desde Internet**.

**6. Un servidor de verdad: la nube y SSH.** En lugar de comprar hardware (on-premise), se alquila una máquina virtual en la nube: es IaaS, porque el proveedor da la máquina y la red, y yo instalo todo lo demás. En clase se usaron máquinas de Oracle Cloud, con los puertos abiertos en sus reglas de red. Para administrarla a distancia se entra por **SSH** con un par de claves: la pública en el servidor y la privada en mi equipo, sin contraseña y sin acceso de root. Para subir ficheros sueltos existen FTP (inseguro), FTPS y SFTP, que va dentro de SSH. La máquina ya es accesible, pero solo por su IP: **nadie se aprende una IP**.

**7. Un nombre para la máquina: DNS.** Se compra un dominio y en su zona se crea un registro A que apunta a la IP pública del servidor (AAAA para IPv6, CNAME para alias, MX para el correo). Cuando alguien escribe el nombre, un resolutor recursivo pregunta a la raíz, al TLD y al servidor autoritativo y le devuelve la IP. Además, sin un dominio que apunte al servidor, Let's Encrypt no puede comprobar que es mío y no da certificado. Con todo listo, desplegar a mano en el servidor sería lento y arriesgado: copiar, parar, arrancar y cruzar los dedos. **Hace falta automatizarlo**.

**8. Desplegar con un comando: Kamal.** Kamal construye la imagen Docker, la sube a un registro, entra por SSH en el servidor, la descarga y arranca la versión nueva junto a la vieja. kamal-proxy, que escucha en el 80 y el 443, espera a que `/up` responda 200, cambia el tráfico y retira la vieja: sin corte. Con `proxy.host` y `ssl: true` pide solo el certificado de Let's Encrypt, y como reparte por la cabecera `Host`, varias aplicaciones conviven en el mismo servidor. Hay dos destinos, staging para probar y production para los usuarios, y `kamal rollback` vuelve a la versión anterior si algo sale mal. La aplicación ya está en Internet, pero cualquiera puede ver y tocar todas las tareas: **hay que saber quién es cada uno**.

**9. Usuarios: autenticación y autorización con JWT.** Al registrarse, la contraseña se guarda como hash Argon2, nunca en claro. Al iniciar sesión, el backend compara el hash y devuelve un JWT firmado con el id del usuario y una caducidad. El cliente lo manda en la cabecera `Authorization: Bearer` en cada petición: eso es la **autenticación** (quién eres). Después el backend decide qué puede hacer ese usuario, por ejemplo ver solo sus tareas: eso es la **autorización**. El JWT no cifra nada, solo firma, así que todo tiene que ir por HTTPS. En una empresa con muchos servicios, los usuarios se centralizan en un directorio LDAP, para entrar en todos con la misma cuenta. Añadir usuarios obliga a cambiar la base de datos, y esa base ya está en producción con datos reales: **no se puede borrar y empezar de nuevo**.

**10. Cambiar la base sin perder datos: migraciones.** Con Alembic, cada cambio del esquema es una revisión numerada que sabe aplicarse (`upgrade`) y deshacerse (`downgrade`). En la API de tareas, la revisión de usuarios creó la tabla `users`, añadió el dueño a cada tarea y asignó las tareas antiguas a un administrador. El protocolo: copia de seguridad, probar primero en staging, migrar producción a una hora de poco uso, desplegar y, si falla, volver atrás por las dos vías (la imagen con `kamal rollback` y la base con `alembic downgrade` o la copia). Con tantos pasos, un fallo pequeño puede tirar la aplicación: **cada cambio debería comprobarse antes de desplegar**.

**11. Cerrar el círculo: integración continua.** Cada push a Git lanza un pipeline en GitHub Actions: instalar dependencias, formato y estilo con Ruff, tipos con mypy, tests con cobertura mínima, seguridad con Bandit, pip-audit y Gitleaks. Lo barato va primero y, si algo falla, no se despliega. En el caso práctico, `just deploy` ejecuta todas esas comprobaciones antes de llamar a Kamal. Y así se vuelve al principio: un cambio nuevo en Git, comprobado, desplegado en staging, después en producción, sin corte y con vuelta atrás.

**Cómo contarlo en el examen.** Una frase de entrada con la idea («desplegar es llevar una aplicación de mi ordenador a los usuarios de forma segura, repetible y sin cortes»), el recorrido con cada paso enlazado al siguiente por el problema que deja abierto, y un cierre que vuelva a Git y a la integración continua. Si da tiempo, añadir un esquema con las cuatro capas o con el despliegue de Kamal.

### Errores típicos

- **Hacer una lista de unidades sin conexión.** Lo que se valora es entender por qué hace falta cada pieza. Cada párrafo debería terminar con el problema que resuelve el siguiente.
- **Olvidar el DNS en la historia.** Sin dominio no hay nombre que recordar ni certificado de Let's Encrypt.
- **Decir que JWT o Basic Auth cifran.** El único que cifra es TLS (HTTPS).
- **Poner la nube antes que el servidor web.** Primero se entiende y se monta en local; luego se lleva a un servidor de verdad.
